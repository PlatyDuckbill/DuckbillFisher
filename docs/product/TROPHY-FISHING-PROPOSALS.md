# 터주작 중심 후속 기능 후보

기록: 2026-10-18, 상태 갱신: 2026-10-21. 사용자가 터주작 중심의 진행을 선택하고 아래 다섯 제안을 문서에 보관하도록 요청했다. 1·2·5번은 이후 합의·구현·배포했다. 2번 출현 일정표는0.5.0.0 고정 Release 대표 확인 뒤 게시했으며, 전수/실제 저장소 업데이트 확인은 별도다. 3·4번의 착수·순서는 아직 결정하지 않았다. 먼바다 상세 보강은 후속으로 둔다.

## 후보 목록

| 번호 | 후보 | 사용 목적 | 구현 전 확인·결정할 사항 |
|---|---|---|---|
| 1 | 미끼 준비 확인(완료) | 목표 터주의 권장 미끼와 소지 수량을 비교하고 부족한 준비물을 모아 표시 | 0.3.0.0 미끼 준비·찾기로 배포. 소지품 조회 범위·미조회/0개 구분과 생미끼 선행 어종 안내는 해당 기능 계약을 따름 |
| 2 | 출현 일정표 | 즐겨찾기/현재 필터 어종의 여러 출현을 시간축으로 비교 | 공개0.5.0.0 고정 Release 대표 확인 완료. 기본3시간·조밀한 시간축과 월 달력/날짜별 회차 목록. [동작·범위](SPAWN-SCHEDULE.md) |

| 4 | 실시간 직감 상태 | 실제 직감 버프의 활성 여부·남은 시간을 타이머에 표시 | KR 상태 ID/남은 시간/수명/로그아웃 처리의 관찰 근거. 선행 어획 진행도는 별도 검증 후 가능 범위만 지원하며, 미관찰을 0회로 추정하지 않음 |
| 5 | 터주작 진행 현황(완료) | 지역·확장팩별 수집/남은 터주 수를 요약하고 해당 목록으로 이동 | 0.4.0.0 수집 현황으로 배포. 확장팩→지역·전체/터주/터주왕·먼바다 해역·중복 제거·Unknown 구분·독립 클릭 목록 제공 |

1번은 [미끼 준비·찾기](BAIT-PREPARATION.md)로 구현해 0.3.0.0에, 5번은 [수집 현황](../verification/catalog/UI.md#0400-수집-현황과-메인-진입-2026-10-20)으로 0.4.0.0에 배포했다. Release 추출본 대표 확인과 실제 친구 업데이트·전체 테마 확인은 구분한다. 현재 상태는 [STATUS](../STATUS.md)를 따른다. 남은 3·4번 후보의 착수 순서는 미결정이다.

## 기존 기능과의 관계

- 1번은 기존 F09의 ‘게임 미끼 선택 화면에서 추천 미끼 강조’와 다른 기능이다. 소지 수량 비교가 신규 범위다.
- 2번은 기존 출현 예측/남은 시간 정렬을 활용하는 새 일정 표현이다. 예측 공식을 변경하는 제안이 아니다.
- 2번은 [출현 일정표 동작과 HTML 시안](SPAWN-SCHEDULE.md)에 합의한 화면·대상·시간 비교·날짜 선택·미확인 처리를 정리했다. 고정 Release 대표 확인/원격 게시와 전체 조합 전수 확인은 구분한다.
- 3번은 기존 즐겨찾기와 필터 프리셋에 목표 묶음 개념을 더하는 제안이다. 현재 알림 정책을 자동으로 바꾸지 않는다.
- 4번은 기존 직감 필요 어종/마릿수의 정적 안내와 구분되는 실제 버프 관찰이다. 정적 자료의 지속 시간 미확인을 관찰값으로 임의 보충하지 않는다.
- 5번은 기존 등급·수집·지역 자료를 집계하는 새 요약 표현이다. 수집 Unknown은 미수집으로 세지 않고 별도로 구분한다.

## 착수 경계

- 다음 구현을 정할 때 후보·작은 첫 범위·완료 기준을 선택한다. 별도 화면이나 주요 배치 변경은 사용자에게 질문하고 답변 후 구현한다.
- 공개 API 우선, 네이티브 관찰은 정확한 KR 근거와 Plugin 경계를 유지한다. 조회 불가·마지막 표본·실제 현재 상태를 구분한다.
- 준비물이나 버프 일부가 확인되어도 실제 어획 가능·개인 준비 완료를 확정하지 않는다. 게임 조작·자동 미끼 변경·런타임 HTTP는 추가하지 않는다.
- 기존 수집/수동 우선·필터 저장/프리셋·알림·캐릭터 격리 정책을 유지한다. 각 후보가 정책 변경을 요구하면 별도로 결정한다.
- 먼바다·작살, 입질 초 수 통계, 복수 어획·수량, Teamcraft/바다구렁이 불일치는 기존 후속/보류 상태를 유지한다. 이 문서 기록으로 재개하지 않는다.

현재 구현·실제 확인 범위는 [STATUS](../STATUS.md), 기존 확정 기능은 [PRODUCT](PRODUCT.md), 전체 후보는 [ROADMAP](ROADMAP.md)을 따른다.

## 다음 추천 어종 알고리즘 초안 (2026-10-24)

사용자가 현재 시점에서 다음으로 도전할 어종을 추천하는 기능의 알고리즘을 질문했다. 아래는 검토 초안이며 추천 기능·별도 화면·주요 동선은 아직 구현하거나 합의하지 않았다. 우선 목표는 ‘기회가 드문 어종’과 ‘준비가 쉬운 어종’ 중 선택을 확인 중이다.

### 후보와 준비 계획

- 첫 범위 제안은 일반 낚시의 미수집 목표다. 즐겨찾기/현재 필터 중 대상 범위를 선택하는 방식과 화면 위치는 구현 전에 합의한다. 수집 Unknown은 미수집으로 간주하지 않고, 조건 Unknown·먼바다/작살은 확정 추천과 분리한다. 추천은 기존 필터/알림 대상을 자동으로 바꾸지 않는다.
- 기존 `FishingForecast`의 출현/직감 구간을 재사용하되 이것만으로 개인 준비 완료를 판정하지 않는다. 현재 예측은 직감 선행 어종의 조건 구간을 반영하지만 실제 마릿수 달성·생미끼 준비 소요 시간·버프 활성 상태를 뜻하지 않는다.
- 대상의 `BaitSteps`와 직감 `Predators`를 준비 의존 관계로 펼친다. 생미끼는 순서가 있는 단계, 같은 단계의 미끼 후보는 대안, 직감 선행 어종들은 필요한 마릿수를 포함한 전체 요구 조건이다. 직감용 어종의 생미끼 연쇄도 포함한다. 원본에 없는 경로 조합이나 다른 낚시터 간 생미끼 유지 가능성을 만들지 않는다. 순환/누락/중첩 미지원은 확인 필요로 남긴다.
- 준비 부담은 최대 생미끼 깊이, 필요한 전체 선행 어획/직감 마릿수, 선행 어종별 조건 구간, 낚시터 이동 필요 여부를 각각 보관한다. 최대 깊이 하나로 전체 부담을 대표하지 않는다. 공통 조건 계산은 재사용하되 필요한 어획 횟수를 임의로 합쳐 줄이지 않는다.
- 준비물은 조회가 확인된 첫 실제 미끼만 비교한다. 수량 Unknown과0개를 구분하고, 중간 생미끼가 가방에 없다는 이유로 불가 처리하지 않는다. 실제 버프/생미끼 보관/직감 진행도 활용은 기존 검증된 관찰값을 연결할 별도 범위로 둔다. 미관찰을0마리 또는 준비 완료로 해석하지 않는다.

### 가능성 판단 후 우선순위

1. 각 후보를 ‘조건상 도전 후보 / 선행 준비 우선 / 출현 대기 / 확인 필요’로 나누고 근거를 붙인다. 제한이 없는 직감 선행 어종도 마릿수 준비가 필요하므로 직감을 단순 가산점이나 고정 감점으로 처리하지 않는다.
2. 현재/다가오는 출현의 끝까지 실제로 쓸 수 있는 시간을 본다. 도착·준비 시간의 근거가 있으면 `종료 - max(출현 시작, 현재 + 이동 + 준비)`를 도전 여유로 사용한다. 첫 버전은 성공률/입질 초/개인 준비 분을 만들어 넣지 않고, 확인된 조건 구간과 상대 준비 부담을 표시한다. 시간 추정치를 도입하면 사용자가 지정한 값/가정임을 표시하며, 가정만으로 불가능을 확정하지 않는다.
3. 준비 가능성과 충분한 도전 여유를 먼저 비교한다. 준비를 시작해야 할 시점도 고려해서 아직 출현 전인 직감 목표가 준비 대상으로 올라올 수 있게 한다. 보관/유효 기간·실제 진행이 미확인인 경로는 준비 가능성을 확정하지 않는다.
4. ‘기회 우선’은 위 판단 뒤 다음 기회까지의 간격·현재 회차 종료의 긴급도·준비 부담을 비교한다. ‘쉬운 도전 우선’은 준비 부담·현재 도전 여유를 앞에 둔다. 재출현 간격은 기존 예측의 제한된 범위에서 계산하고, 다음 회차 미발견을 무한 희귀도로 간주하지 않는다. 첫 버전부터 임의 가중치 하나로 모든 조건을 합치지 않는다.
5. 추천에는 ‘생미끼2단계·직감용3마리 준비 필요’, ‘현재 회차 잔여 시간 짧음’, ‘다음 회차까지 오래 남음’ 같은 이유와 미확인/가정 여부를 함께 제공한다. 특정 어종 수치가 아닌 표시 예시다. 완수율/성공 확률을 주장하지 않는다. 순위가 초 단위로 흔들리지 않도록 재계산 경계와 동률 정렬을 고정한다.

### 구현 책임 제안

- Core는 시각을 인자로 받는 준비 의존 관계·우선순위·이유 코드만 계산한다. Plugin은 캐릭터/소지 미끼 등 검증된 관찰을 관리 값으로 복사하고 표시 시 TextKey로 번역한다.
- 정적 의존 관계는 자료 변경 때 구성하고, 출현/재출현 계산은 제한된 기간·후보 수로 캐시한다. Draw에서 전체 재검색/장기 예측을 하지 않는다. 캐릭터/대상/자료 변경·언로드 시 오래된 요청과 결과를 폐기한다.
- 첫 구현은 추천 어종과 이유 확인에 집중한다. 자동 이동·미끼 변경·시전·서버 채팅·런타임 원격 조회는 추가하지 않는다. 기능 배치와 우선순위 합의 후 구현 범위를 확정한다.

## 현재 낚시터 출현 알림 논의 (2026-10-24)

- 사용자 요청으로 다음 추천 알고리즘 논의보다 먼저 다룬다. 알람 상한120분은 반영하고, 아래 신규 기능의 배치/출력 방식은 논의 단계다.
- 요청은 최근 낚시터가 아닌 현재 낚시터가 인식될 때, 그 낚시터의 미수집 터주/터주왕이 출현하기 시작하면 텍스트도 포함해 알리는 것이다. ‘팝업’은 어종의 출현 시작으로 우선 해석하며 UI 팝업 표시 방식은 아직 합의하지 않았다.
- 기존 `FishingTracker`는 진행 중인 낚시의 확인된 위치와 `LastKnown`/최근 기록을 구분한다. 현재 지역에 서 있는 것만으로 정확한 낚시터를 판정하지 않는다. 현재 세션/읽기 정상·확인된 위치만 사용하고, 낚시 종료·이동·관찰 실패에서는 현재 알림 감시를 중단하는 방향을 제안한다. 새 게임 접근은 이번 논의에서 구현하지 않는다.
- 설정 위치 제안: 기존 즐겨찾기 관리 → 출현 알림 설정 안에 ‘즐겨찾기 출현 알림’과 ‘현재 낚시터 출현 알림’을 독립 켜기/끄기 구역으로 둔다. 후자는 즐겨찾기 여부/메인 필터와 독립인 미수집 터주·터주왕 대상이며, 수집 Unknown을 미수집으로 처리하지 않는다.
- 출현 시작 전이를 관찰해 회차별1회 발송하고 이미 출현한 어종의 낚시터 최초 인식/재로드 때 소급할지는 별도 동작으로 결정한다. 기존 즐겨찾기 알림과 같은 회차가 겹칠 때의 중복 출력도 구현 전에 정한다.
- 예측은 현재 확인된 낚시터의 조건/날씨 연결을 확인해 사용한다. 기존 권장 낚시터 기준 결과를 다른 낚시터의 결과로 간주하지 않는다.
- 텍스트는 본인 로컬 채팅에 어종/낚시터/출현 시작·남은 시간/직감 필요 여부를 안내하는 방식을 우선 제안한다. 타이머 내 표시·별도 화면 팝업 여부, 채널·소리 공유 여부는 미결정이다. 실제 어획 준비 완료를 뜻하지 않으며 Toast를 임의로 복구하지 않는다.
