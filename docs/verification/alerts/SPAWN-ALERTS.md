# MVP-03/F05 출현 사전 알림 첫 구현

날짜: 2026-10-16 · Plugin 0.1.20.0 · 사용자 알림 대표 동작 확인

후속: 사용자 ‘잘 동작하는듯 함’으로 대표 확인을 받았다. 모든 경계/재로드/절전 확인을 뜻하지 않는다. 즐겨찾기 스크롤과 어종별 설정·채널·SE·기록·메시지 피드백은 [0.1.21.0 작업](ALERT-MANAGEMENT.md)에서 처리한다. 아래는 첫 구현 당시 범위/실행 기록이다.

## 범위와 사용자 동작

- `/duckbillfisher` → `출현 알림` 탭에서 로컬 채팅 알림 켜기/끄기와 실제 1~60분 전을 설정한다. 기본은 꺼짐/5분이다.
- 공통 즐겨찾기 + 현재 캐릭터의 최종 `Uncaught`만 대상이다. 기존 수동 지정 우선순위를 그대로 사용한다. Unknown/Caught/먼바다/상시/예측 미지원은 제외한다.
- 목록 검색·수집/지역/등급 필터와 독립적이다. 예측은 내장 조건의 권장 낚시터 기준이다. 현재 지역 필터로 알림 낚시터를 바꾸지 않는다.
- 첫 채널은 `IChatGui.Print`의 본인 로컬 채팅이다. 서버 송신 없음. Toast/선택 소리는 후속 범위다.
- 어종명·낚시터·현지 창 시작 시각과 일반 시간·날씨 예측이라는 안내를 출력한다. 미끼·직감·전승록·물고기의 눈 등의 개인 준비나 실제 어획 가능성을 확정하지 않는다.
- 동시 도달한 알림은 1초 표본당 메시지 하나로 묶는다. 채팅에는 최대 3종과 나머지 개수를, 탭에는 마지막 묶음 전체를 표시한다. `Sent`는 로컬 출력 큐에 넣은 어종 수이며 실제 화면 노출 확인과 구분한다.

## 예약·중복·수명

- Core `SpawnAlertScheduler`: UTC/단조 경과 시각/세션/설정/관리 데이터만 받는다. 미래 알림 시각을 예약한 후 그 시각을 지나는 표본에서만 발송 후보가 된다.
- 현재 열린 창이나 알림 시간이 이미 지난 창은 건너뛴다. 짧은 창이 이어져도 다음 창을 예약하도록 기존 `FishingAvailability.Find`를 창 종료 시각부터 재사용한다. 기존 공식·조건 JSON은 변경하지 않았다.
- 후보당 최대 64창을 탐색하고 결과를 캐시하며, 1초 표본당 새 계획은 최대 8종으로 나누어 처리한다. 실패한 계획은 단조 시간 기준 1분 후 재시도한다. Framework에서만 실행하며 Draw에서 시트/파일/장기 예측을 읽거나 계산하지 않는다.
- 최초 로드, 로그인/캐릭터 변경, 알림 활성화/사전 시간 변경에는 지난 알림을 재생하지 않는다. 새로 미수집이 확인되거나 즐겨찾기로 추가된 어종도 미래 알림만 예약한다.
- 표본 간 경과가 10초 초과이거나 UTC 변화와 단조 경과 차이가 2초 초과이면 그 표본의 발송을 생략하고 미래 예약으로 복귀한다. 절전/긴 지연/시계 변경 뒤 밀린 알림을 보내지 않는다.
- 설정 schema v2는 v1의 즐겨찾기/캐릭터별 수동 상태를 보존하며 알림 기본값을 추가한다. 다음 실제 저장 때 v2로 기록한다. 구버전 플러그인으로의 설정 하향 호환은 제공하지 않는다.
- 캐릭터/FishParameter별 마지막 발송 예약 창의 시작 Unix 밀리초를 저장한다. 같은 시작 또는 이전 창은 재발송하지 않아 재로드·시간 역행·사전 시간 변경으로 인한 중복을 막는다. 캐릭터 ID는 로컬 설정 키에만 쓰며 진단에는 넣지 않는다.
- 저장 API가 성공한 후에만 채팅 큐에 넣는다. 저장 실패는 출력 중단/오류 표시, 출력 실패는 재전송하지 않는다. 저장 직후 종료되면 알림을 놓칠 수 있으며 중복 방지를 우선한다. 하드웨어/파일 손상 복구까지 보장하지 않는다.
- 세션 변경 때 메모리 예약/마지막 묶음/집계를 폐기한다. Framework 구독은 Dispose에서 해제한다. 자동 수집 관찰은 기존과 같이 세션 메모리이며 발송 기록과 별개다.

## API 근거와 실행한 검사

- 현재 참조 `XIVLauncherKR/addon/Hooks/dev/Dalamud.dll` 15.0.3.6과 동봉 XML을 개발 중 읽기 전용으로 조사했다. 기존 KR 네이티브 게이트는 수정하지 않았다.
- `IChatGui.Print(string, string, ushort?)` → `PrintTagged` → 로컬 `chatQueue.Enqueue` 경로를 확인했다. 게임 명령/키 입력/서버 채팅 API를 추가하지 않았다.
- `IDalamudPluginInterface.SavePluginConfig` → `PluginConfigurations.Save`는 `ReliableFileStorage.WriteAllTextAsync(...).GetAwaiter().GetResult()` 완료를 기다리는 것을 설치 DLL IL에서 확인했다. 외부 설정/계정 자료는 읽지 않았다.
- 별도 빌드: `dotnet build src/DuckbillFisher.Plugin/DuckbillFisher.Plugin.csproj --no-restore -c Debug "-p:DalamudLibPath=${env:DALAMUD_HOME}/" "-p:OutputPath=${env:DUCKBILL_ROOT}/.cache/spawn-alert-build/"`.
- 별도 빌드 경고·오류 0. `pwsh -NoLogo -NoProfile -File scripts/check-localization.ps1`: 한영 265키/형식 인자 일치. `git diff --check` 통과. 테스트는 요청이 없어 추가/실행하지 않았다.
- 별도/정규 산출물 확인: 주 DLL 937472바이트/0.1.20.0, Core 39424바이트/1.0.0.0, ko 리소스 30720바이트/0.1.20.0, manifest DuckbillFisher/0.1.20.0/API 15. 교체 전 정규 DLL 914432바이트/0.1.19.0 유지도 확인했다.
- 사용자 ‘언로드 완료’ 후 OutputPath 지정 없는 정규 빌드 경고·오류 0, 한영 265키 검사를 재확인했다. 0.1.20.0 로드/실제 알림/설정 유지/중복·복귀 동작은 인게임 검증 대기다.
- Teamcraft/바다구렁이 차이는 [기존 기록](../forecast/OPEN-WINDOW-DIAGNOSTICS.md)의 미해결 후속 조사로 유지한다. 이번 작업에서는 재조사/로그 요청/예측 공식 변경을 하지 않았다.

## 첫 인게임 확인

1. 0.1.20.0 로드 후 `출현 알림` 탭 기본 꺼짐/5분, 한영 전환 시 설정/예약 상태 유지 확인.
2. 실제 미수집이며 일반 제한 창이 곧 오는 어종 하나를 즐겨찾기에 추가한다. 필요 시 게임 도감으로 상태를 확인하거나 명시적으로 수동 미수집을 지정한다. 창 시작까지 남은 시간이 사전 시간보다 커야 한다. 예: 시작 3분 이상 남았을 때 사전 1분 설정.
3. 알림 켜기 → 탭의 다음 알림/창 시작 시각 확인 → 창 시작 약 X분 전에 본인 채팅에 한 번 출력되는지 확인. 창을 닫아도 예약은 작동해야 한다. 보고는 이 탭의 `짧은 알림 진단 복사`만 사용한다.
4. 같은 창에서 끄기/켜기·시간 변경·언로드/재로드를 해도 같은 창이 다시 출력되지 않는지 확인. 재로드 전 새 언로드 절차를 따른다.

추가 확인 대기: 알림 직전 즐겨찾기 해제/수집됨 지정/Unknown 전환 시 취소, 동시 여러 어종 묶음, 긴 중단/절전 복귀, 설정 저장 실패, 실제 다른 캐릭터 격리. 사용 가능한 다른 캐릭터가 없어도 이번 대표 확인을 막지 않는다. 과거 통과한 지도 핀·등록·수집 숨김 검사를 반복하지 않는다.

## 0.3.6.0 알림 예약 결함 수정 (2026-10-19)

플러그인 자체 결함 점검에서 알림 계획과 발송 판정 사이의 실행 순서를 검토했다. 아래는 코드 경로로 확인한 문제이며 게임에서 재현한 결과는 아니다.

| 경로 | 기존 문제 | 수정 |
|---|---|---|
| UTC 역행·긴 관찰 중단 | Scheduler는 그 표본의 발송을 생략했지만 Plugin의 미래 계획/실패 재시도는 남았다. 예를 들어09:30에10:00 출현을 예약한 뒤08:30으로 돌아가면 새로 미래가 된09:00 출현을 건너뛸 수 있었다(마지막 영속 예약보다 나중인 출현 기준) | 기존 재기준화 판정을 부작용 없는 `RequiresRebase`로 공유하고, 새 후보를 만들기 전에 계획/재시도/순회 위치를 초기화한다 |
| 대량 즐겨찾기·실패 재시도 | 매번 같은 순서에서 새 계산8종을 소모했다. 결과 없는 앞쪽 항목이1분 뒤 재시도되면서 뒤쪽의 최초 계산을 계속 밀어낼 수 있었다 | 마지막 계산 다음 위치부터 순환한다. 기존 예약은 예산과 무관하게 매 표본 확인하고 상시 출현은 계산 예산에서 바로 제외한다 |

- 기존 UTC/단조 시간 차이2초 초과·표본 간10초 초과·세션/활성화 변경 기준은 유지했다. 시계가 바뀐 표본의 소급 발송은 계속 금지한다.
- 1초당 새 계획8종·실패1분 재시도·일반 기준 예측·캐릭터별 영속 중복 방지·저장 후 로컬 출력은 유지한다. 대량 목록을 한 번에 계산하거나 이미 지난 알림을 따라잡지 않는다.
- 저장·기록/게임 API·네이티브 지원 계약·데이터 JSON·진단 alerts/v6 필드는 변경하지 않았다. 이번 수정으로 다른 캐릭터 격리나 저장 장애 실기가 확인된 것은 아니다.

검사: 별도 `.cache/alert-stability-build/`와 정규 Debug 직접 빌드 경고0/오류0, 한영634키/형식 인자·문서 링크·`git diff --check` 확인. 테스트 추가/실행·실제 알림/시계 조작·게임 로드·패키징·게시 없음.

인게임 확인 대기:

1. 곧 출현할 제한 어종에 알림을 설정하고 미래 예약→사전 시각에1회 발송→끄기/켜기 후 동일 출현 중복 없음 확인.
2. 상시/제한 어종이 섞인 여러 즐겨찾기에서 상시는 제외 이유를 유지하고 뒤쪽 제한 어종도 순차 예약되는지 확인. 기존 예약의 마감 시각 확인이 새 계산 대기 때문에 멈추지 않아야 한다.
3. 긴 관찰 중단 후 지난 알림은 발송하지 않고 남은 미래 출현을 새로 예약하는지 확인. UTC 역행은 시각 입력을 제어한 별도 검증이 남아 있으며 사용자 PC 시계 변경을 요구하지 않는다.
## 출현 알림 설정 탭·캐스팅 채널 분리 (2026-10-24)

공개0.5.3.0 이후 개발본의 별도 변경이다. 사용자 합의로 즐겨찾기 관리 안에 `즐겨찾기 / 출현 알림 설정 / 발송 기록`을 배치했다. 가운데 탭에는 메인 설정에 있던 출현 알림 옵션을 옮겼고 톱니는 이 탭을 직접 선택한다. 기본/어종별 사전 시간·대상·소리의 기존 판정과 발송 기록은 유지한다.

- 캐스팅 알림은 기존 타이머 설정 본문 상단에서 전용 채널을 고른다. 공통 출력 설정으로 이동하는 버튼은 제거했다. 입질·터주·터주왕은 기존 소리만 유지하며 채팅 기능을 추가하지 않았다.
- 설정schema22의 `Timer.AlertChannelId`를 검증/복사/비교/저장하고 PrintTimer가 이 값을 사용한다.21 이하 설정과 백업 형식1은 기존 출현 알림 채널을 한 번 복사한다.22 이후부터 두 채널 변경은 독립이다. 프리셋은 알림 목록만 교체하므로 채널은 유지한다.
- 새 게임 API/네이티브·의존성 변경, 서버 채팅 전송은 없다. 기존 Framework의 로컬 XivChatEntry 출력만 사용한다. 테스트는 요청되지 않아 추가/실행하지 않는다.
- 별도 `.cache/alert-settings-build/` → 정규 Debug 경고0/오류0·한영933키/형식 인자·문서110개/로컬 링크547개·diff 검사 통과. 설치된 wasdcxz15.0.3.9 참조를 사용했다. 인게임/백업 복원·패키징·원격 게시 확인과는 구분한다.

대표 확인 대기:

1. 즐겨찾기 관리에 세 탭이 위 순서로 보이고 톱니로 가운데 탭을 선택하는지 확인한다. 메인 설정에는 기존 출현 알림 항목이 없어야 한다. 출현 알림 설정의 WAV 파일 선택·미리 듣기/중지와 한영·좁은 폭도 확인한다.
2. 기존21 이하 설정으로 로드한 첫 캐스팅 채널은 이전 출현 알림 채널과 같아야 한다. 이후 두 채널을 서로 다르게 지정하고 출현 알림/캐스팅 알림이 각 로컬 표시 채널에만 나오는지 확인한다. 각 소리·입질·터주·터주왕 효과음과 발송 기록은 유지되어야 한다.
3. 재로드 후 서로 다른 채널이 유지되어야 한다. 캐스팅 프리셋 불러오기로 채널이 바뀌지 않아야 한다.21 백업을 가져오면 당시 공통 채널을 이어받고22 백업은 각각의 채널을 복원해야 한다.
4. 저장 실패·미지원 채널·세션 전환·모든 언어/폭 조합은 별도 확인 대상이다. 기존 백업·구조·KR 확인 대기는 [STATUS](../../STATUS.md)를 따른다.
