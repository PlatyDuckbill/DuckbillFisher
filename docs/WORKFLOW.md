# 개발 워크플로우

## 작업 단위

한 번에 '캐스팅 감지 구현' 전체보다 '캐스팅 시작을 1회 관찰하고 취소 시 상태를 초기화'처럼 작은 결과를 만든다. 방법은 **짧은 기술 검증 → 작은 기능 구현 → 자동 검증 → 실제 게임 확인**이다.

각 작업은 다음 다섯 항목을 먼저 정한다.

| 항목 | 예시 |
|---|---|
| 사용자 동작 | 직접 찌를 던지면 타이머가 시작된다 |
| 범위 | 시작/취소 상태와 표시만, 입질 예측은 다음 작업 |
| 근거 | 대상 Dalamud revision에서 확인한 API/소스 |
| 자동 검증 | 중복 시작, 취소, 새 시전의 상태 전이 |
| 게임 완료 기준 | 시작 1회, 취소/로그아웃 시 초기화, 재로드 후 중복 없음 |

## Windows에서 개발과 게임 확인

2026-10-15부터 FFXIV가 실행되는 Windows PC에서 AI 보조 편집·Git 관리·빌드·인게임 확인을 진행한다. Mac은 초기 환경 구축과 참조 컴파일의 이력이며, 매 작업에서 두 PC를 왕복하지 않는다. 첫 전환과 새 세션 시작은 [세션 인수인계](SESSION-HANDOFF.md)를 따른다.

1. 같은 Windows 소스 폴더를 열고 `git status`와 STATUS의 다음 한 작업을 확인한다. 필요하면 작은 기능 브랜치를 만든다. 기존 수정은 보존한다.
2. AI와 작은 변경을 구현하고 사람이 범위·동작·설계 이유를 검토한다. 대상 API는 현재 KR 설치를 기준으로 확인한다.
3. 먼저 별도 출력 경로로 Plugin을 빌드한다. 사용자에게 언로드 완료를 확인받은 뒤 아래 명령으로 정규 DLL을 빌드한다. 테스트는 사용자가 요청한 경우에만 실행한다.

```powershell
dotnet build src/DuckbillFisher.Plugin/DuckbillFisher.Plugin.csproj --no-restore -c Debug -p:DalamudLibPath=C:/Users/hyogu/AppData/Roaming/XIVLauncherKR/addon/Hooks/dev/
pwsh -NoLogo -NoProfile -File scripts/check-localization.ps1
```

4. 성공한 출력 DLL을 로드하고 게임 행동은 사람이 직접 수행한다. 실제 결과가 없으면 인게임 검증 대기로 남긴다. 빌드 실패 시 기존 DLL로 검증을 계속하지 않는다.
5. 실패하면 같은 PC에서 관련 오류 구역과 재현 순서를 확인해 수정한다. 기본은 짧은 진단이며 전체 진단은 필요한 경우에만 파일이나 해당 구역으로 받는다. 성공/실패·미실행 항목은 [검증 기록](templates/VALIDATION.md)에 구분해 남긴다.
6. STATUS와 필요한 HANDOFF를 갱신하고 완료한 작업 범위를 명시적으로 스테이징해 커밋한다. 인게임 확인 대기 상태도 구분해 기록한다. 커밋 SHA·검증 결과를 보고하며 푸시·배포는 별도로 취급한다. 상세 규칙은 AGENTS.md의 '작업 완료와 커밋'을 따른다.

등록한 DLL 경로는 `src\DuckbillFisher.Plugin\bin\Debug\DuckbillFisher.dll`의 절대 경로다. 소스 폴더를 옮겼을 때만 개발 플러그인 등록 경로를 바꾸고, 이전 경로와 중복 등록하지 않는다. 전용 개발 폴더 복사는 선택이다.

원격 저장소가 준비된 후 소스를 동기화할 때는 먼저 로컬 수정을 확인하고, 수정이 없는 경우 `git pull --ff-only`를 사용한다. 원격 실행이나 게임 PC의 CI runner는 현재 필요하지 않다.

## 빌드 파이프라인 목표

- `global.json`으로 .NET SDK 10.0.402를 고정했다. 생성한 의존성 lock 파일도 소스와 함께 버전 관리한다.
- Windows 개발 PC: Core 테스트, 대상 한섭 참조 Plugin 빌드, manifest/패키지 검사.
- 일반 CI/보조 Mac: 게임과 독립된 Core 빌드·테스트, 데이터 스키마/참조 검증. 기존 교차 플랫폼 구성은 유지한다.
- 게임 테스트: 사용자가 직접 로드·언로드·기능 확인. CI 성공과 별도로 기록한다.
- Plugin CI는 build/dalamud-reference.json에 고정한 upstream 참조를 체크섬 검증 후 사용한다. 이 컴파일 성공을 한섭 런타임 호환성으로 표현하지 않는다. 실제 GitHub Actions 실행은 첫 푸시 이후 확인한다.
- 준비된 스크립트는 빌드 실패 시 배포하지 않고, 목적 경로를 명시적으로 받고, 플러그인 자신의 파일만 다뤄야 한다.
- 개발 빌드 자동 복사는 가능하지만 게임 조작 자동화는 범위 밖이다.

## 코드 리뷰 기준

| 영역 | 검토 항목 |
|---|---|
| C# / .NET SDK | csproj 참조, 대상 런타임, SDK 호환성 |
| 인터페이스 / nullable | 의존성 경계, 값 없음과 false의 구분 |
| 이벤트 / IDisposable | 구독 해제, 재로드 시 중복 방지 |
| async / 스레드 | UI·게임 API 스레드 제약, 백그라운드 계산 분리 |
| 네이티브 포인터 | 버전별 구조와 객체 수명, 잘못된 접근의 영향 |
| 테스트 / 로그 | 컴파일, 계산 정확성, 인게임 동작의 검증 범위 구분 |
| 문자열 / 다국어 | 리소스 키·형식 인자·누락 번역 fallback·고정 ImGui ID·언어와 독립된 보고서 |
| 유지보수 | UI/상태/게임 접근/표현의 책임 분리, 타입으로 상태 표현, 불필요한 추상화와 중복 방지 |

변경마다 설계 이유, 실패 조건, 검증 결과를 리뷰한다. AI 보조 구현에도 같은 기준을 적용한다.

## 모델과 스킬 운용 제안

이는 모델의 성능 보장이 아니라 프로젝트 운영 규칙이다.

현재 기반 구성과 Windows 기본 관찰 검증은 완료되었으므로 Sol 6.1을 기본으로 사용한다. 설계 판단이나 재현이 어려운 결함이 있을 때 Astra 검토를 추가한다.

- Astra: 초기 경계 설계, 한섭 호환성의 불확실성 분석, 네이티브 연동 설계 검토, 재현이 어려운 결함.
- Sol 6.1: 완료 기준이 정해진 기능, 테스트, UI 수정, 데이터 검증, 문서 갱신.
- 모델을 바꿀 때 대화 전체를 전달하기보다 STATUS의 근거·미확인 사항·다음 작업을 읽게 한다.
- 큰 설계 변경과 정책 판단은 별도 작업으로 분리한다. 단순 구현마다 상위 모델 검토를 의무화하지 않는다.

처음에는 AGENTS.md와 이 문서들로 충분하다. 동작하지 않은 절차를 스킬로 굳히지 않는다. 첫 Windows 검증 이후 다음 세 가지 반복 절차를 프로젝트 스킬로 만들 수 있다.

| 만들 스킬 후보 | 만들 시점 | 담을 내용 |
|---|---|---|
| 한섭 API 근거 확인 | 첫 어댑터 검증 후 | 버전 확인, 소스 탐색, API 존재/스레드/수명 확인 |
| Windows 빌드·검증 | ENV-02 통과 후 | 실제 경로와 스크립트, 로드/언로드, 로그 수집 |
| 어종 데이터 검수 | 첫 데이터 5~10종 검증 후 | 출처/라이선스, ID 참조, 패치 범위, 조건·입질 구간 검증 |

외부 범용 스킬을 일괄 설치할 필요는 없다. C# 개발은 저장소 지침·컴파일러·테스트가 중심이며, 스킬은 확인된 반복 절차를 재사용하는 용도다. 이번에는 커스텀 스킬을 생성/설치하지 않았다.
